## 1. 产品概述

### 1.1 一句话定位

RainCode 是一个面向个人开发者的本地优先 AI 编程工作台：由 Agent 内核驱动终端 CLI 与 Windows 桌面端双端一体，在用户的真实代码仓库中完成开发、调试、重构、测试与文档等工程任务；数据全本地，模型自由接入。

### 1.2 价值主张

- **把 Agent 交给个人**：不依赖团队级平台与云服务，一个开发者、一台机器、自己的 API Key，即可获得对齐 Claude Code / OpenAI Codex 行业水平的代码 Agent 能力。
- **上下文留在本机**：代码、会话、记忆、配置全部落在本地，出网的只有用户显式发起、发往用户自选 Provider 的模型请求。
- **终端与桌面同一大脑**：CLI 与桌面端共享同一 Agent 内核与会话存储，终端里开始的任务可在桌面端无缝续接。
- **成本自己说了算**：按 token 直连模型厂商计费，可随时切换到本地开源模型（Ollama）实现零 API 成本。

### 1.3 设计原则

| 原则 | 含义 | 落地约束 |
| --- | --- | --- |
| 本地优先 | 单机可完整运行，不依赖任何自建云服务；无账号体系、无强制登录 | 会话数据存储于本地 SQLite + JSONL；断网时仍可浏览历史会话、使用本地模型 |
| 隐私可控 | 代码与上下文仅流向用户明确配置的目标 | 每次模型请求只发往用户配置的 Provider baseURL；无遥测上报；API Key 仅存本地 |
| 成本可控 | 用量透明、可切换 | Token 用量逐请求统计并展示；支持低成本/免费 Provider 与本地模型一键切换 |
| 可扩展 | Provider、工具、能力四层开放扩展点 | OpenAI 兼容协议接入任意模型；工具/MCP/技能斜杠命令/插件分层扩展（见第 5 章） |

### 1.4 产品形态与交付节奏

- **双端一体**：CLI（TUI，Ink 实现）+ Windows 桌面应用（Electron + React 18 + Zustand + Tailwind CSS），两端共享同一 Agent 内核、同一套会话持久化数据；P2 阶段补齐 Web 界面。
- **迭代顺序（已确认）**：Agent 内核 → CLI → 桌面端。先让内核与 CLI 达到 P0 可用，再以桌面端 Alpha 覆盖 P1 能力，最后在 P2 完成七模块全量对齐。
- **技术栈基线**：TypeScript 全栈；Node.js ≥ 20；pnpm monorepo；存储采用 better-sqlite3（SQLite）+ JSONL 会话流；数据结构校验统一使用 zod。
- **模型接入基线**：统一 OpenAI 兼容协议（Chat Completions + SSE 流式）；Provider 可配置四要素 baseURL + apiKey + model + maxContextTokens；内置预设 OpenAI / DeepSeek / Kimi / GLM / Ollama。

### 1.5 里程碑总览

| 里程碑 | 对应优先级 | 范围 |
| --- | --- | --- |
| M1 | P0 | Agent 内核 + 基础工具集 + 权限审批闭环 + 会话持久化 + CLI TUI，CLI 达到日常可用 |
| M2 | P1 | 上下文压缩、MCP 接入、子代理、项目记忆 + 桌面端 Alpha |
| M3 | P2 | 沙箱容器（Docker/WSL）、技能与斜杠命令扩展、插件化、远程执行、Web 界面，七大模块全量对齐行业水平 |

## 2. 目标用户画像

RainCode 面向**个人开发者**，不设团队协作与组织管理能力。三类典型画像：

### 画像 A · 独立开发者 / 自由职业者

- **特征**：同时维护 2~5 个个人项目或外包项目，Node.js/Python 为主力栈，对成本敏感。
- **痛点**：没有团队分担重复劳动；既想要 Agent 干活，又不想把客户代码上传到第三方云端工作台。
- **典型用法**：CLI 为主，在项目根目录直接 `raincode` 启动；用 DeepSeek / GLM 等高性价比 Provider 跑日常任务，重要任务切旗舰模型。
- **关键诉求**：数据不出本机、成本逐条可查、CLI 快（冷启动快、审批不打断心流）。

### 画像 B · 企业内资深工程师（个人提效场景）

- **特征**：在职工程师，公司设备涉密或有合规限制，禁止使用云端 AI IDE 处理工作代码。
- **痛点**：Claude Code / Trae 等产品需要账号与云侧上下文，合规上过不去；自己搭脚本式工具链又太原始。
- **典型用法**：桌面端为主做代码库理解与重构评审，CLI 做批量脚本化任务；Provider 指向公司内网网关或本地 Ollama。
- **关键诉求**：无强制账号、权限三态默认收紧（ask）、审批记录可追溯、API Key 支持内网自托管端点。

### 画像 C · AI 工具重度玩家 / 开源爱好者

- **特征**：持续追踪 Agent 领域进展，动手能力强，喜欢折腾本地模型、MCP 服务器与自定义技能。
- **痛点**：现有产品模型绑定或黑盒封装，想换模型、加工具、改提示词都要等官方支持。
- **典型用法**：CLI + MCP + 子代理 + 自定义技能组合出个人工作流；关注版本节奏与扩展点文档。
- **关键诉求**：Provider/工具/MCP/技能/插件全链路开放，schema 清晰（zod 单一事实源），可以自己写扩展。

### 2.4 共性需求汇总

三类画像的诉求收敛为以下共性需求，直接对应第 5 章功能模块：

| 共性需求 | 来源画像 | 对应模块 |
| --- | --- | --- |
| 数据不出本机，无强制账号 | A / B | 全局设计原则（本地优先，见 1.3） |
| 模型可自由切换，成本透明 | A / C | Agent 内核 Agent Core（AC-4 / AC-10 / AC-11） |
| 敏感操作可拦截、可追溯 | B | 命令权限控制 Permission Control（PC-1 ~ PC-5） |
| 快速理解陌生代码库 | A / B / C | Tool System（glob/grep/read）+ Project Memory（MR-1） |
| 长任务可中断、可续做 | A / C | Agent Core（AC-5 / AC-8）+ Project Memory（MR-2） |
| 深度定制个人工作流 | C | MCP Integration、Sub-agent Manager、技能与斜杠命令、插件化 |

## 3. 核心使用场景

以下 10 个场景覆盖 P0~P2 全部核心能力，每个场景按「触发 → 交互 → 结果」描述。Agent 行为均由 Agent 内核的 turn 循环驱动（模型响应 → 工具调用 → 结果回填 → 继续推理）。

### 场景 1 · 新功能开发

- **触发**：开发者拿到需求，如“给 CLI 加一个把当前会话导出为 Markdown 的命令”。
- **交互**：在 CLI/桌面端用自然语言描述需求 → Agent 用 glob/grep/read 摸底现有命令注册与渲染代码 → 生成 todo 计划并逐项执行 → write/edit 落地代码 → 请求运行构建与测试（bash，按权限策略审批）。
- **结果**：产出可编译、测试通过的代码改动；会话中保留完整计划与改动摘要；用户在 Git diff 中复核后决定是否提交。

### 场景 2 · Bug 修复

- **触发**：用户粘贴一段报错堆栈或描述异常现象。
- **交互**：Agent 用 grep 定位报错源码 → read 相关文件形成根因假设 → bash 最小化复现 → edit 修复 → bash 执行回归测试（审批后运行）。
- **结果**：输出根因分析、修复 diff 与验证结果三段式结论；用户确认后可继续让 Agent 完成 commit。

### 场景 3 · 代码库理解

- **触发**：新接手陌生仓库，或需要向他人解释某模块。
- **交互**：提问“登录鉴权链路是怎么走的” → Agent 并行执行 glob/grep/read 扫描关键文件 → 输出带文件路径引用的链路说明。
- **结果**：得到可追溯（每条结论可定位到文件）的架构摘要；用户确认后可将其沉淀进 MEMORY.md 项目记忆，后续会话自动带上。

### 场景 4 · 重构

- **触发**：“把这个 800 行的 service 拆成职责清晰的模块。”
- **交互**：Agent 先产出拆分计划（todo 跟踪）→ 逐文件 edit → bash 全量编译 + 测试 → 对未通过项迭代修复。
- **结果**：结构化拆分完成且全量回归通过；过程中的每一次写操作与命令执行均按权限三态控制，可随时拦截。

### 场景 5 · 测试生成

- **触发**：“给 utils/date.ts 补齐单元测试。”
- **交互**：read 目标文件与既有测试样例 → 识别测试框架与断言风格 → write 新测试文件 → bash 执行 → 失败用例自动迭代。
- **结果**：新增测试文件全绿通过，风格与仓库既有测试一致。

### 场景 6 · 文档生成

- **触发**：“为这次改动补充 README 章节 与 API 文档。”
- **交互**：Agent 读取本次会话中的改动与相关代码 → 生成文档草稿 → write 到目标文件。
- **结果**：与代码同步的文档草稿，用户编辑确认后入库；文档内容可标注来源文件便于复核。

### 场景 7 · Git 操作辅助

- **触发**：“把刚才的改动按逻辑拆成 3 个 commit，写清楚提交信息。”
- **交互**：Agent bash 执行 git status/diff → 分析改动分组 → 逐条 git add + commit（每次执行前 ask 审批）。
- **结果**：干净、语义化的提交历史；每一步命令用户都可批准或拒绝，不会出现未经确认的仓库操作。

### 场景 8 · 脚本自动化

- **触发**：“写个脚本把 dist 产物按版本号归档并生成 sha256 清单。”
- **交互**：Agent write 脚本 → bash 试运行 → 根据输出修参数 → 归档到 scripts 目录。
- **结果**：可复用的自动化脚本与一次成功运行的记录，后续可封装为技能/斜杠命令（P2）。

### 场景 9 · 跨会话长任务续做

- **触发**：昨天的重构做到一半，今天继续。
- **交互**：`raincode --resume` 选择历史会话（1 万条消息内 ≤ 1s 恢复）→ Agent 依据会话流与 todo 状态汇报进度 → 用户确认后续做。
- **结果**：无需重新交代背景，任务从中断点继续；依赖会话持久化（SQLite + JSONL）与项目记忆系统（P1）。

### 场景 10 · 本地模型离线/零成本模式

- **触发**：无外网环境，或用户不想为轻度任务消耗 API 额度。
- **交互**：在设置中把 Provider 切换为 Ollama（本地模型）→ 继续使用全部工具链与权限体系。
- **结果**：零 API 成本完成代码理解、小改动等任务；体验与云端模型一致，仅响应速度取决于本地硬件。

### 3.11 场景与能力映射

| 场景 | 依赖核心能力 | 最早可用里程碑 |
| --- | --- | --- |
| 1 新功能开发 | Turn 循环、基础工具集、权限审批、todo 计划 | M1 |
| 2 Bug 修复 | grep/read 定位、bash 复现与回归、edit 修复 | M1 |
| 3 代码库理解 | 并行 glob/grep/read、记忆沉淀 | M1（MEMORY.md 沉淀为 M2） |
| 4 重构 | todo 跟踪、批量 edit、全量 bash 回归 | M1 |
| 5 测试生成 | read、write、bash 执行迭代 | M1 |
| 6 文档生成 | 会话内改动感知、write | M1 |
| 7 Git 操作辅助 | bash + 逐条审批 | M1 |
| 8 脚本自动化 | write、bash 试运行 | M1（封装为技能为 M3） |
| 9 跨会话长任务续做 | 会话持久化、--resume、会话记忆 | M1（会话记忆增强为 M2） |
| 10 本地模型零成本模式 | Provider 切换、Ollama 预设 | M1 |

> M1 即可支撑场景 1~10 的基本闭环；M2/M3 通过压缩、记忆、扩展体系提升同类场景的体验上限。

## 4. 竞品对比与差异化

### 4.1 竞品概览

**Claude Code（Anthropic）**

- 形态：终端 CLI 为主，配套 IDE 扩展与桌面端；Agent 编程能力的行业标杆。
- 优势：MCP、子代理、hooks、CLAUDE.md 记忆、权限模式、沙箱等能力完整，社区生态成熟。
- 局限：模型绑定 Anthropic 服务，需账号/订阅；模型选择权与数据流向受制于官方体系。

**OpenAI Codex CLI（OpenAI）**

- 形态：Rust 实现的 CLI + IDE 扩展 + 云端任务。
- 优势：审批分级清晰、AGENTS.md 记忆、系统级沙箱，CLI 开源便于研究。
- 局限：以 OpenAI 系模型为主，第三方模型支持有限；深度使用依赖 ChatGPT 账号体系。

**ZCode（开源项目，本地参考竞品）**

- 形态：桌面（Electron）+ Web + TUI 三入口，统一 `zcode` 命令启动；Agent CLI 同时作为桌面与 Web 的运行时。
- 优势：Provider 可配置、支持 SSH/WSL 远程执行、全栈开源、本地运行，与 RainCode 形态最接近。
- 局限：体系偏重（客户端 / 后端 / 共享 UI 多包协同），面向更广人群；个人轻量使用的安装与资源门槛偏高。

**Trae（字节跳动）**

- 形态：AI IDE（VS Code 分支）+ SOLO 自主任务模式。
- 优势：开箱即用、内置托管模型、IDE 体验完整。
- 局限：深度绑定平台账号与云端上下文体系，代码上下文在云侧流转，个人可控性与合规性弱。

> 注：竞品能力基于截至 2026-09 的公开资料整理，用于定位参考，具体以各产品官方文档为准。

### 4.3 差异化优势

1. **本地优先，隐私可控**：会话、配置、记忆、审批记录全部落在本地 SQLite + JSONL，无强制账号、无遥测；代码上下文只在用户显式发起请求时流向用户自选的 Provider。对画像 B（合规受限工程师）是唯一可行解。
2. **模型自由，成本透明**：统一 OpenAI 兼容协议，任意 Provider（含 Ollama 本地模型）改配置即切换；自带 API Key 按量直连，逐请求 token 统计，成本直接对账单，不被订阅制绑定。
3. **双端一体共享后端**：CLI 与桌面端共享同一 Agent 内核与会话存储——终端里开始的会话在桌面端打开即续接，审批记录两端一致，不存在“两个产品两份数据”。
4. **轻量个人向**：单机运行、Node.js ≥ 20 即装即用，无云服务依赖、无团队协作包袱；CLI 冷启动 ≤ 2s 的硬指标保证“打开就干活”。
5. **扩展链路全开放**：Provider、工具、MCP、技能/斜杠命令、插件四层扩展点全部面向用户开放，数据结构以 zod schema 为单一事实源，个人可定制程度高于闭源 IDE 型产品。
6. **路线透明可验收**：七大模块按 P0/P1/P2 明确排期（M1/M2/M3），用户可按里程碑逐项验收，功能对齐 Claude Code / OpenAI Codex 的公开能力矩阵。

### 4.4 定位结论

- Claude Code / OpenAI Codex CLI 验证了“终端 Agent + 工具调用 + 权限审批”是个人编程 Agent 的正确形态，但两者的模型绑定与账号体系把“模型选择权”和“数据流向”从用户手中拿走。
- ZCode 验证了多模型 Provider 与双端形态的可行性，但其工程体量面向更广人群；RainCode 以“轻量、个人、单机”为第一约束做减法，聚焦个人开发者的日常闭环。
- Trae 代表“云端托管、开箱即用”路线，与 RainCode 的“本地优先、自己掌钥”处于两极；对合规敏感与成本敏感用户，RainCode 是替代选择而非跟随者。
- **RainCode 的站位：形态对齐 Claude Code / Codex，路线对齐 ZCode 的多模型开放，立场坚持本地优先与个人轻量**，以 M1 → M2 → M3 三个里程碑完成七大模块全量对齐。

## 6. 非功能需求与性能指标

### 6.1 性能指标基线表（正式定稿）

| 编号 | 指标 | 目标值 | 定义 | 测量方式 |
| --- | --- | --- | --- | --- |
| NFR-1 | CLI 冷启动 | ≤ 2s | 从 shell 执行 `raincode` 到 TUI 渲染完成、可接受用户输入的时长（不含模型请求） | 进程启动至 TUI ready 事件本地计时打点；开发基准机取 20 次中位数 |
| NFR-2 | 用户输入→模型请求本地开销 | ≤ 300ms | 用户确认发送后，本地完成上下文组装、zod 校验、消息落盘、HTTP 请求发出的总时长（不含网络传输与模型响应） | 发送确认时间戳与请求发出时间戳之差；取 P95 |
| NFR-3 | 工具结果本地渲染延迟 | ≤ 100ms | 工具执行返回到端侧（CLI/桌面端）完成结果渲染的时长 | 工具完成事件至渲染完成事件打点；取 P95 |
| NFR-4 | 桌面端空载内存 | ≤ 500MB | 主进程 + 渲染进程 + Agent 运行进程空载驻留内存之和（启动后无会话活动 5 分钟） | Electron process.memoryUsage 汇总 + 系统任务管理器交叉验证 |
| NFR-5 | 会话恢复 | ≤ 1s（1 万条消息内） | 选中历史会话到消息流完整加载、可继续交互的时长 | 恢复开始至渲染完成打点；使用 1 万条消息规模的样本会话 |
| NFR-6 | 上下文压缩异步不阻塞 | 压缩期间交互零阻塞 | auto-compact 执行期间，用户输入、工具调用与审批不被阻塞；压缩完成前旧上下文持续可用 | 压缩窗口内注入输入与工具调用探测用例，验证无排队等待；纳入回归测试 |
| NFR-7 | 崩溃后会话数据 100% 可恢复 | 100% | 任意时刻进程被强杀（如 kill -9 / 任务管理器结束）后重启，已交互消息与审批记录零丢失 | 自动化测试：会话进行中随机时刻强杀进程，重启后校验 JSONL 完整性与消息计数一致（依赖 JSONL 追加写） |

> NFR-6/NFR-7 为约束型指标（无量化阈值），验收方式为专项用例通过；其余指标在 Windows 10/11 基准开发机（Node.js ≥ 20）上测量。

### 6.2 其他非功能需求

| 类别 | 要求 |
| --- | --- |
| 可靠性 | SQLite 开启 WAL；消息流 JSONL 逐条追加落盘，落盘粒度为单条消息 |
| 安全与隐私 | API Key 仅存本地配置（可选系统凭据库加密），不写入日志与会话流明文；无遥测上报；默认权限三态中未知操作为 ask |
| 兼容性 | Windows 10/11 优先支持（桌面端首发 Windows），macOS/Linux 跟进；Node.js ≥ 20；出网目标仅限用户配置的 Provider baseURL、MCP Server 与远程执行目标 |
| 可维护性 | TypeScript 全栈、pnpm monorepo 统一工程化；所有对外数据结构以 zod schema 为单一事实源 |
| 可扩展性 | Provider / 工具 / MCP / 技能与斜杠命令 / 插件分层扩展点，各层互不耦合 |
| 合规与许可 | 第三方依赖合规清单与许可声明随版本发布维护 |

### 6.3 存储与数据需求

| 数据 | 载体 | 说明 |
| --- | --- | --- |
| 会话元数据 | SQLite（better-sqlite3，WAL 模式） | 会话列表、标题、时间、Token 用量汇总等可索引字段 |
| 会话消息流 | JSONL 追加写 | 消息、工具调用、工具结果、审批记录逐条追加，是崩溃恢复的事实来源 |
| 项目记忆 | MEMORY.md | Markdown 文件，用户可直接编辑，会话启动时注入上下文 |
| 配置 | 本地配置文件 | Provider 四要素（baseURL/apiKey/model/maxContextTokens）、权限规则、MCP 服务器清单；API Key 支持系统凭据库加密存储 |

### 6.4 约束与假设

- 约束：单机运行，不自建任何云端服务；出网仅限 Provider baseURL、MCP Server、SSH/WSL 远程目标三类用户显式配置的目标。
- 约束：桌面端首发 Windows（Electron + React 18 + Zustand + Tailwind CSS），CLI 跨平台；Node.js ≥ 20；pnpm monorepo 统一管理。
- 假设：用户自行保管 API Key 并承担模型调用费用，产品不代理、不转售模型额度。
- 假设：沙箱容器能力（Docker/WSL）依赖用户本机已安装相应运行时；未安装时降级为“工作目录约束 + 权限三态控制”的组合防线。

## 7. 成功标准

### 7.1 M1（P0：Agent 内核 + CLI 可用）

- **功能验收**：
  - Agent 内核 turn 循环与流式输出稳定可用，长任务（20+ 工具调用）中可中断、可恢复；
  - OpenAI 兼容接入在五个内置预设 Provider（OpenAI / DeepSeek / Kimi / GLM / Ollama）中至少各实测 1 个模型连通并完成一次真实任务；
  - 基础工具集七工具（bash/read/write/edit/glob/grep/todo）全部可用，参数经 zod 校验；
  - 权限三态 allow/ask/deny 与 CLI 审批闭环完整走通，审批记录可查；
  - 会话可创建、列表、恢复、删除，崩溃恢复测试通过率 100%（NFR-7）。
- **任务样例验收**：在真实开源仓库中，Agent 独立完成“修复一个含复现步骤的 Bug”全流程（定位 → 修复 → 测试 → 汇报），人工仅参与审批。
- **性能验收**：NFR-1 / NFR-2 / NFR-3 / NFR-5 / NFR-7 全部达标。

### 7.2 M2（P1：MCP / 子代理 / 记忆 / 压缩 + 桌面端 Alpha）

- **功能验收**：
  - auto-compact 在长会话中自动触发，压缩期间交互零阻塞（NFR-6 专项用例通过），压缩后任务上下文连续性人工验收通过；
  - stdio 与 HTTP 两类 MCP Server 各接入 ≥ 1 个真实服务，其工具纳入权限三态控制；
  - 子代理完成至少一次“多子任务委派 + 结论回传”，主上下文无子任务中间过程污染；
  - MEMORY.md 与会话记忆在新会话中生效，--resume 续做场景可用；
  - 桌面端 Alpha 覆盖会话管理、工作区选择、权限审批弹窗、Provider 设置四项，且与 CLI 共享同一会话数据、审批记录两端一致。
- **性能验收**：NFR-4（空载内存）达标；NFR-6 专项验证通过。

### 7.3 M3（P2：沙箱容器 / 技能扩展 / 插件 / 远程执行 + 七模块全量对齐）

- **功能验收**：
  - Docker / WSL 沙箱可选启用，启用后文件系统与网络隔离策略生效（越界操作被拦截）；
  - 用户可自定义技能与斜杠命令并被 Agent 加载执行，官方提供 ≥ 3 个示例技能；
  - 插件机制可用并发布 ≥ 1 个示例插件；
  - SSH/WSL 远程执行完成端到端任务（远程仓库修改 → 远程测试 → 结果回传）；
  - Web 界面可用；
  - 七大功能模块（Agent 内核、工具调用系统、MCP 调用、子代理管理、沙箱执行环境、命令权限控制、项目记忆系统）能力清单全量交付。
- **对齐口径**：第 4.2 节对比矩阵中 RainCode 列各项能力全部落地，与 Claude Code / OpenAI Codex CLI 公开能力完成对标。
- **性能验收**：NFR-1 ~ NFR-7 全部达标；远程执行场景下 NFR-2 的本地区间开销仍 ≤ 300ms。

### 7.4 验收方式说明

- **性能指标**：以本地计时打点脚本 + 自动化基准会话（含 1 万条消息样本集）测量，每个里程碑发布前执行一轮并留存数据；NFR-6 / NFR-7 属约束型指标，以专项用例通过与否则定。
- **功能验收**：以第 5 章功能点编号为清单逐项核对；每个里程碑附一组“真实仓库任务样例”作为端到端验收（M1 的 Bug 修复样例、M2 的 MCP / 子代理 / 记忆样例、M3 的远程执行样例）。
- **对齐验收**：M3 以第 4.2 节对比矩阵中 RainCode 列为核对表，逐项确认落地。
- **回归保障**：Agent Core、Tool System、Permission Control、会话持久化四条核心链路自 M1 起建立自动化回归用例，随里程碑持续扩充。

| 审批闭环 | ask 类操作从“暂停 → 用户批准/拒绝 → 执行或终止 → 记录落盘”的完整流程 |
| auto-compact | 接近上下文上限时对历史消息进行后台摘要压缩的机制 |
| 会话流 | 以 JSONL 追加写形式落盘的单会话全部事件（消息、工具调用、审批记录） |
| 项目记忆 | 以 MEMORY.md 为载体的项目级长期记忆，会话启动时注入上下文 |
