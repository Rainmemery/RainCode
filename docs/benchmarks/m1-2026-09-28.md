## 3. 测量方式明细（对照 01-PRD §6.1「测量方式」列）

- **NFR-1**：spawn `node --import tsx apps/cli/src/index.ts ping` 子进程，计时起点为 spawn 前，终点为 stdout 首个版本输出（"novacode agent service ok / protocol: 1.0"）——对应「进程启动至 TUI ready 事件本地计时打点」（当前 CLI 为 readline 形态，stdout 版本输出即可接受交互的等价打点）；同一临时 NOVACODE_HOME 连续 20 次，取中位数，附 P95。
- **NFR-2**：`t0` = 用户确认发送（`beginTurn` 内发起 `session.send` 前打点）；`t1` = mock LLM 服务器捕获请求体时刻（p0-lib `bodyTimes`，`performance.now()` 同进程时钟）；差值含 rpc 装配、zod 校验、用户消息 JSONL 落盘、上下文组装、工具 schema 编码、HTTP 请求发出。每轮迭代新建会话（上下文恒定）；轮询等待粒度 ≤1ms（计入误差方向为偏保守）。
- **NFR-3**：进程内 harness（07 §2.4 口径「CLI 侧」）。`tool_call.completed` 事件到达客户端回调即打点，执行与 `apps/cli/src/stream.ts` 完全等价的 completed 渲染分支（单行折叠 + 截断 + 同步 `write` 调用，写丢弃 sink 等价 `process.stdout.write`）；同时记录服务端发布时刻（`event.ts`）→ 渲染完成的全链路口径。工具为只读 `read`（metadata 快速通道放行）。
- **NFR-5**：`Storage.createSession` 后向 events.jsonl 批量写入 1 万条合法 message 行（seq 2~10001，无 checkpoint——即 full-replay 最坏路径），随后每轮 `Storage.open` + `storage.resumeSession`（含增量重放/悬挂补齐/message_count 对账回写全流程）计时，共 10 轮取中位数。
- **NFR-7**：spawn CLI 子进程 `novacode run "<prompt>" --yes`（env 注入 mock Provider），mock 首轮回放 bash 工具调用（`ping -n 8 127.0.0.1` 慢命令跨 shell 可执行），父进程观察到 CLI 渲染 `▸ bash` 后 800ms（工具执行窗口、JSONL 静默期）执行 `taskkill /F /T /PID` 强杀；随后重开 Storage 断言四项（文件完整性 / 已完成消息零丢失 / 悬挂 tool_call 以 `msg_recovered_*` isError=true 补齐 / message_count 三方一致）后打印 PASS。`--times N` 可扩展为 07 §2.4 的强杀 ×20 全量验收口径，本轮按单轮专项用例执行（4 项断言全通过）。

## 4. 结论

- M1 性能验收项 NFR-1 / 2 / 3 / 5 / 7 **全部达标**（07-dev-plan §2.4 / 01-PRD §7.1）。
- 各项相对目标余量：NFR-1 约 4 倍、NFR-2 约 18 倍、NFR-3 全链路亚毫秒、NFR-5 约 10 倍；NFR-7 专项断言全通过。
- 下一轮（M2 验收）复跑 `bench:start / send / resume` 应满足「不劣化（±10% 内）」的对比基准即为本文件数据。
